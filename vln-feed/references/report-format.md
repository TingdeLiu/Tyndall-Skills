# VLN 周报格式与分析准则

按本文件生成 `reports/vln_<YYYY-MM-DD>.md`。报告服务于地面机器人 VLN / 具身导航研究决策，不是资讯搬运清单。

## 一、写作流程

1. 汇总本次新增条目，记录标题、日期、来源、原文链接和本地文件。
2. 用方法名、论文标题、arXiv ID、项目链接合并公众号与 arXiv 重复项。
3. 为每个独立工作标注相关度：
   - `A`：直接研究地面 VLN、ObjectNav、语言/语义导航、长期导航或真机导航。
   - `B`：不是目标任务，但有可明确迁移的记忆、规划、纠错、地图、评测或系统机制。
   - `C`：无人机、机械臂、自动驾驶或通用模型动态，仅作领域观察。
4. 先形成跨条目的趋势判断，再选择 3–5 个 A 级工作做深度分析。
5. 逐项回查原始条目。数字必须附任务/数据集/指标；链接必须属于当前工作。
6. 按下方模板写报告并运行 `scripts/validate_report.py`。

## 二、全篇不用表格（2026-09-27 起）

报告会原样发布到博客，读者多在手机上看。宽表格在窄屏上要左右滑动，单元格里的长句还会被挤成一列细条，用户明确反馈「看起来非常不方便」。因此：

- **全篇禁止 Markdown 表格**，包括两列的「维度 | 分析」表。`validate_report.py` 会拦截。
- 多字段信息改用两种写法：
  - 列表项 + 子列表：`- **[工作名](链接)** · 场景`，下挂 `- 贡献：…`、`- 证据：…`。
  - 加粗标签起段：`**问题。** 一段话。`，适合深度分析这类长文本。
- 次池的大量工作按主题写成一行一组：`- **主题（N）**：[工作A](链接)、[工作B](链接)…`，链接由脚本从 `items/` 生成。

## 三、固定结构

```markdown
# 具身导航周报（YYYY-MM-DD，覆盖 YYYY-MM-DD ~ YYYY-MM-DD）

## 一、本期结论

- 3–5 条跨论文结论。每条说明“发生了什么 → 为什么重要 → 对地面 VLN 的影响”。

## 二、优先阅读清单

1. **[方法名](原文链接)** · 任务/场景
   - 贡献：一句话。
   - 证据：数据集 + 指标 + 数值，或“未提供可核验数字”。
   - 理由：为什么值得读。

## 三、重点工作分析

### 1. 方法名：一句话判断

**问题。** 现有方法的具体瓶颈。

**方法。** 关键机制及其作用链条。

**证据。** 数据集、指标、对照和数字；缺失时如实说明。

**价值。** 对地面 VLN/导航的直接价值。

**局限。** 泛化、真机、算力、数据或评测限制。多条时改用无序列表。

**建议。** 值得复现、跟踪或借鉴的具体部分。

## 四、可迁移方法

- **来源方向：[工作](链接)**
  - 机制：可迁移的机制与支撑数字。
  - 接入位置：可接入地面导航的哪个环节。
  - 前提与风险：……

只收录迁移路径能说清楚的 B 级工作；不要因为热度高而收录。

## 五、分类速览

开头一句说明相关度 A/B/C 的含义。每个工作一行：

### 5.1 地面 VLN / ObjectNav / 语义导航

- **工作名**（主题 · 相关度）：一句话贡献。[原文](链接)

### 5.2 记忆、地图、规划与评测

同上。

### 5.3 具身 VLA / 移动操作

同上；次池条目多时按主题一行一组。

### 5.4 无人机、自动驾驶与其他低相关方向

同上；每项只写一行。

### 5.5 资讯与非论文

- **日期 · 事件**（类型）：与研究的关系。[链接](链接)

## 六、趋势判断与行动建议

### 趋势

- 写 2–4 条由多项工作共同支持的趋势，不重复摘要。

### 研究空白

- 写 1–3 个尚未解决、且与地面 VLN 直接相关的问题。

### 建议动作

按优先级分组，每组下列出动作：

**高优先级**

- **精读 / 复现 / 跟踪 / 暂缓** 对象：原因。
```

## 四、信息密度规则

- 优先阅读清单控制在 5–8 项；深度分析控制在 3–5 项。
- 同一工作只出现一次详细分析；在分类速览再次出现时写“见重点分析”，不要复制段落。
- 列表项写短句；需要展开的内容放在“重点工作分析”。
- 分类速览覆盖本次所有独立工作。大量 C 级条目保持一行，不展开摘要。
- 公众号与 arXiv 同题时，将公众号视为解读来源，不当成第二篇工作。
- 主题统计放在“趋势判断”中用于支撑结论，不写“本期很丰富”等空泛总结。

## 五、证据与判断

- 使用“论文报告/摘要称……”描述作者结论；使用“本报告判断……”标识分析推断。
- 不把 benchmark 提升等同于真实部署能力；仿真结果与真机结果分开写。
- 数字缺少指标名、数据集或对照时，不写进“证据”。
- 只有摘要时，不推断训练规模、模型组件、项目页或实验设置。
- 发现来源冲突时列出冲突，不自行选择更好看的数字。

## 六、禁止项

- 禁止任何 Markdown 表格（见第二节）。
- 禁止 `![](...)`、`<img>`、`<figure>`、微信图片域名及任何图片占位符。
- 禁止整段复制公众号宣传文案或论文摘要。
- 禁止为每篇低相关论文写长段落。
- 禁止使用未经条目验证的项目链接、作者、机构、会议和 benchmark 数字。
- 禁止“重磅、炸裂、暴涨、遥遥领先、完美解决”等宣传措辞。
