# 完整示例：术语原文 → 大白话

## 原话（用户看不懂的那一条）

> 把 `/camera/image_raw` 的 QoS 从 RELIABLE 改成 BEST_EFFORT，depth 设为 1。
> 当前 DDS 层因为订阅端处理速度跟不上发布频率，队列持续积压，导致下游 tf 变换的
> 时间戳滞后约 400ms，进而让局部规划器基于过期位姿做决策，出现绕圈行为。

---

## 重讲之后

**一句话：** 机器人在拿 0.4 秒前的旧画面做决定，所以老绕圈；改个设置，让它宁可丢几张图，也只看最新的那张。

**打个比方——传送带上的照片：**

- 摄像头 = 一个不停拍照的人，每秒拍 30 张，拍完往传送带上放。
- 处理画面的模型 = 传送带尽头看照片的人，他每秒只看得完 10 张。
- 传送带本身 = 底下真正负责搬消息的那套东西，原话叫 `DDS`。
- 现在传送带的规矩（`QoS`，就是收发消息的规矩：丢不丢得起、能排几条队）写的是 `RELIABLE`——「一张都不能丢」，每张照片都必须被看到。于是照片在传送带上越堆越多（原话叫「队列积压」），他手里那张已经是 0.4 秒前拍的了。
- 「机器人此刻在哪、朝着哪」这个信息（原话叫「位姿」，由 `tf` 负责报）也就跟着晚了 0.4 秒。
- 决定下一小步往哪挪的那段代码（原话叫「局部规划器」）照着 0.4 秒前的世界做决定，等它真走到，世界早变了 → 于是原地绕圈。
- 改法 `BEST_EFFORT` + `depth=1`（「尽力送到，丢了拉倒」+「排队位置只有一个」）= 不再要求每张都看，传送带上只放得下一张，新照片直接把旧的盖掉 → 他手里永远是刚拍的。

**〈比方 = 真实〉对照表：**

| 比方里的 | 实际是 |
| --- | --- |
| 不停拍照的人 | 摄像头节点，发 `/camera/image_raw`（`src/drivers/cam_node.py`） |
| 传送带 | `DDS`，底下真正搬消息的那层 |
| 传送带的规矩 | `QoS` 配置：`RELIABLE` / `BEST_EFFORT`、`depth` |
| 传送带上堆着的照片 | `/camera/image_raw` 的待处理队列（现在积压 ~400ms） |
| 尽头看照片的人 | 模型节点（`src/percep/node.py`），每秒只处理得完 10 帧 |
| 「他手里那张是几点拍的」 | `tf` 报出来的位姿时间戳 |
| 照着旧照片决定往哪走的人 | 局部规划器 —— 绕圈就是它干的 |

```
改之前（一张都不能丢）
 摄像头 ─▶ [旧][旧][旧][旧][新] ─▶ 模型拿到的是最左边那张
                                     （0.4 秒前拍的）

改之后（只留最新一张）
 摄像头 ─▶ [    新    ] ─▶ 模型拿到的就是刚拍的
             旧的直接被盖掉
```

**具体到你这件事：**

- **动哪个文件、哪个参数**：传送带两头的人都得换规矩 = 发消息那边（摄像头节点，`src/drivers/cam_node.py`）和收消息那边（模型节点，`src/percep/node.py`），两处的 `QoS` 都从 `RELIABLE` 改成 `BEST_EFFORT`、`depth` 从 10 改成 1。两边写的不一样会直接连不上，只改一边等于没改。
- **改完会看到什么现象**：绕圈没了；画面偶尔跳一下是正常的——那就是被新照片盖掉的旧照片。跳帧不等于改坏了。
- **下一步做什么**：跑一遍，用 `ros2 topic delay /tf` 盯住「我现在在哪」这个信息（`tf` 报的位姿）还晚不晚 0.4 秒。降到 50ms 以内才算改对。
- **什么情况下会出事**：这一路图像如果要录下来做离线评测，丢帧 = 数据缺了一块，传送带上必须一张不漏。那种情况得保住 `RELIABLE`，改成让传送带尽头的人看快点（模型跑快点），或者让放照片的人放慢点（摄像头降到 10Hz）。

> 哪一块还是糊的？点出来，我只把那一块再拆细。

## 这个例子做对了什么

- **一句话结论放最前**，40 字以内，先说「拿旧画面做决定」这个因果，而不是先说改哪个参数。
- **一个比方贯穿到底**：传送带。摄像头、模型、`DDS`、两种 `QoS` 设置、跳帧，全都在这一个比方里有角色，中途没换成别的比喻。
- **原词和白话并排，不另起术语表**：`QoS`、`RELIABLE`、位姿、局部规划器，全都在读者读懂的那一句里就地解释完。末尾再列一张表是同一件事做两遍，没人会往回翻。
- **落地时把角色对回实物**：「传送带两头的人」后面紧跟着「= 发消息端和收消息端」，再跟上两个真实路径。只写「两边都要改」，用户会卡在「哪两边」。
- **锚点原样保真**：`/camera/image_raw`、`src/percep/node.py`、`depth` 从 10 改成 1、`ros2 topic delay /tf`——这些不需要解释，需要的是照抄。读者就是靠它们在自己屏幕上对号入座的。全换成「那个话题」「那个节点」，比方再好也落不了地。
- **数字有参照物**：`400ms` 变成「0.4 秒前拍的」，还和「等它走到世界早变了」绑在一起。
- **图只画差别所在**：只有「前 / 后」两种队列，因为核心差别就是队列长度。没有硬凑一张分层图。
- **译者不是编辑**：「两边都要改」「什么时候不该这么改」是原话里没明说、但简化后必须补回的前提和风险。省掉它们就等于改了结论。

## 反例：同一段原话，写成「只有故事」的样子

> **一句话：** 机器人在用过时的信息做判断，所以老绕圈。
>
> **打个比方——传送带上的照片：** 想象一条传送带……（此处 12 行，把拍照的人、传送带、
> 尽头看照片的人、照片越堆越多、他手里的照片越来越旧，讲得活灵活现）
>
> **具体到你这件事：** 把消息传输的可靠性策略调低，队列深度设小，让下游只处理最新数据。
> 收发两端都要配置一致。改完观察一下延迟是不是降下来了。

这一版**每句话都对**，用户也确实看懂了传送带。但他打开编辑器之后不知道动哪儿——这正是
「故事听懂了，我的项目还是不知道怎么了」的样子。缺的是三样：

1. **一个锚点都没有** —— 没有 `/camera/image_raw`，没有 `src/percep/node.py`，没有
   `QoS` / `RELIABLE` / `BEST_EFFORT` / `depth`，没有 400ms。全被抹成了「消息传输」
   「下游」「延迟」。用户没法拿这些词去自己屏幕上找东西，也没法拿去问同事。
2. **比方 12 行，落地 4 行** —— 篇幅比例反了。比方是引桥，这一版把引桥修成了目的地。
3. **判据不可观察** —— 「观察一下延迟是不是降下来了」，降到多少算好？没说。对比正例里的
   「用 `ros2 topic delay /tf` 看，降到 50ms 以内才算改对」。

**自查的快办法：** 把比方那几段整个删掉，只留「具体到你这件事」。剩下的内容如果还能让人
动手，就是合格的；如果剩下一堆「下游」「策略」「配置一致」，那就是比方在替正文顶包。

## 第二例：原话只诊断、没给方案

上面那例原话自带改法。更常见的是原话**只把问题讲了一遍就没了**——这时候「那怎么办」必须补，
但要标明来源。同时这也是「比方写短」的样子：三行就够，因为要解释的东西不多。

### 原话

> `map → odom` 这一段 `tf` 有两个 publisher 在抢：`amcl` 和 `robot_localization` 都在发。
> 下游查到哪个取决于到达顺序，位姿在两套估计之间跳变。

### 重讲之后

**一句话：** 有两个程序在同时报「机器人在哪」，谁的话先到就听谁的，所以位置一会儿一变。

**打个比方——两个人同时报路：** 副驾和后座同时给你报「现在到哪了」，报的还不一样。你没有
规则说该听谁，就是谁先开口听谁的——于是你脑子里的位置一直在两个说法之间跳。
（副驾 / 后座 = `amcl` 和 `robot_localization`，两个都在发 `map → odom`。）

**具体到你这件事：**

1. **这到底是什么** —— 「机器人在哪」这个信息，现在有两个来源在同时往外发，而系统只允许有一个。
2. **出在哪** —— `tf` 树里 `map → odom` 这一段。`amcl` 和 `robot_localization` 两个节点都在发它。
3. **为什么会这样** —— `tf` 不做仲裁，谁发就存谁的；下游查的时候拿到的是最后到的那条。两个
   节点的估计本来就有差，于是查出来的位姿在两套之间来回跳。
4. **现在卡在哪一步** —— **已确认**：两个 publisher 同时存在。**还没验证**：跳变幅度多大、
   是不是所有下游都受影响。

**这段原话没说怎么办，我的建议是：**

- **先花五分钟验证** —— 跑 `ros2 run tf2_tools view_frames`，看 `map → odom` 的
  broadcaster 是不是真的列出两个；再用 `ros2 topic echo /tf` 抓十秒，确认时间戳交替。
  只列出一个，那问题不在这儿，上面的诊断不成立。
- **确认了就这么修** —— 二选一，关掉其中一个：`amcl` 用地图定位、`robot_localization` 融
  合轮速和 IMU，一般保留 `amcl` 发 `map → odom`，把 `robot_localization` 的
  `world_frame` 从 `map` 改成 `odom`（它只发 `odom → base_link`）。改完再跑一次
  `view_frames`，`map → odom` 只剩一个 broadcaster 就对了。
- **不修会怎样** —— 导航还能跑，但路径会周期性抖；一旦上代价地图或做长距离规划，
  抖动会被放大成绕路和撞障碍。属于能拖但越拖越贵那类。

> 比方对得上你的实际情况吗？哪一块还是糊的，点出来，我只把那一块再拆细。

### 这一例的关键

- **原话里没有的方案，单独起了一块**，标题写死「这段原话没说怎么办，我的建议是」。混进
  「具体到你这件事」里就等于把我的判断冒充成原话——那是编辑，不是译者。
- **建议分三层，第一层是验证不是修法。** 诊断还没坐实就甩修法，用户照着改了才发现问题不在
  那儿，比不给方案更糟。
- **比方只有三行。** 要解释的只有「两个来源在抢」这一件事，比方够用就停，剩下的篇幅全给落地。
- **五个槽位里第 4 条把「已确认 / 还没验证」分开写**，用户才知道哪些是结论、哪些还是猜测。
