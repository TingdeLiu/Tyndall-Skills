# 按需使用的纯文本图示

只有当图能减少解释成本时才用。先决定要帮助用户看懂哪一个关系，再选最小的图；同一件事不必同时画流程、比喻对应表和决策树。

下面都是示意，不是对当前项目结构、行为或性能的断言。实际使用时只填入已有证据支持的内容，未知就标明未知。

## 前后对比

适合解释用户可见的行为变化。区分预期变化和已验证结果。

```text
之前：先选 A，再选 B -> A 的旧结果可能覆盖 B
改动：结果返回时检查 -> 只采用最后一次选择的结果
验证：自动测试通过；浏览器里尚未实际验证
```

若一句话就能说明差别，直接用一句话，不必套图。

## 简单流程

适合说明信息或操作经过哪些步骤，箭头表达具体关系。

```text
选择筛选项 -> 请求对应数据 -> 检查是否仍为最新选择
                              | 是：更新页面
                              | 否：忽略旧结果
```

只保留与问题有关的步骤，不为介绍架构而增加无关模块。

## 层级或组成

适合解释整体和部分的关系。

```text
报告
|-- 概览：先看主要结果
|-- 明细：核对单条记录
`-- 导出：保存报告副本
```

不要把层级图当流程图；父子关系不意味着先后执行。

## 多项选择

多个方案按相同维度比较时，优先使用 Markdown 表格，少用需要手工对齐的字符表。仅在选择确实取决于前置条件时使用简短决策树。

```text
离线时需要继续筛选吗？
|-- 需要：考虑离线网页包
`-- 不需要，只看和分享：考虑 PDF
```

这个示意只反映「筛选」这一项条件，不自动说明价格、工期或其他功能优劣。完整语境见 [选择题示例](decision-example.md)。

## 可读性

- 使用代码块保持等宽；图过宽时改成纵向或普通列表，尽量适合窄屏阅读。
- 需要对齐时注意：汉字通常占两个显示列，英文字母通常占一个；不同客户端可能有差异。
- 优先无边框图，用 `->`、`|` 等简单符号连接，避免复杂框线、emoji 或空格对齐表。
- 节点写用户能理解的动作或对象。只有定位、操作需要时才附准确技术名称。
- 图中的数字、完成状态和风险判断与正文遵循相同证据要求，不因放在示意图里就可以编造。
- 删掉图后如果同样容易理解，就删掉它。
