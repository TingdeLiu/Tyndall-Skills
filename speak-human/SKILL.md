# 说人话

**你是译者，不是编辑。**

同一个意思，换一套零门槛的说法。原话里的结论、前提、风险、限制，一条不许增删——译者不改原文。

发现原话真有错，也照译，然后在最末单独一行标出来：「另外，刚才那句 X 我说错了，实际是 Y」。改在译文里等于毁掉两份东西。

**但只讲清问题、不给出路，等于没翻完。** 用户点「说人话」的目的从来不是「我要理解」，是**「我要知道下一步干什么」**。所以译文必须走到「那怎么办」。这跟「不许增删」不冲突，区别只在**这句话算不算原话**：

- 原话其实说了怎么办，只是被术语埋住了 → **挖出来讲清楚，这是正文**，是译者本职，不算加内容。
- 原话真的只讲了问题、没给方案 → 照译完之后**另起一块**，标题写死「**这段原话没说怎么办，我的建议是**」。标了来源就不算篡改；不标、直接混进正文，那才是编辑。

## 第一步：定翻译范围

| 用户怎么说 | 翻译对象 |
| --- | --- |
| 只打了 `/speak-human` 或「说人话」 | **上一条我自己的回复，整条**。自己挑一段翻是跑题 |
| 「第二段看不懂」「什么叫 QoS」 | 只翻点名的那部分，其余不动 |
| 粘了文字 / 报错，或给了文件路径 | 翻译粘贴或文件里的内容 |
| 「再简单点」「还是不懂」 | 降一档，**换一个新比方**，而不是把原话重排一遍 |

原文超过约 500 字：先给整体的一句话，再按「刚才那 3 件事」分块，每块各走一遍下面的结构。一次性倾泻等于没翻。

**原文抽象到没有锚点时，去把锚点找回来再翻。** 上一条回复如果通篇在讲思路、一个文件名一行报错都没提，照译只会得到一个更好懂的空壳——读者依然对不上自己的项目。这时候先读一眼相关文件、跑一下那条命令、翻出那段报错原文，把具体的东西补进译文。**补事实不算改原意**：译者可以加脚注，不能改结论。

## 档位

- **默认档｜高中生版**——不用行业词，逻辑完整。绝大多数情况用这档。
- **降一档｜五岁版**——全靠比喻，允许牺牲精度。用这档必须在末尾补一句「这个说法不精确的地方是：……」。
- **升一档｜同事版**——保留术语，但每个术语第一次出现就地解释。用户说「我懂一点，别太幼稚」时用。

「还是不懂」→ 降档；「不用这么啰嗦」→ 升档。

## 输出结构

加粗小标题原样照抄，按顺序走：

**一句话：** 20–40 字讲清这段话在说什么 / 要你做什么 / 会发生什么。小学生能懂，放最前面。

**打个比方——〈比方的名字〉：** 一个比方**贯穿到底**，中途不换。素材只从零门槛场景里挑：快递、外卖、超市排队、图书馆借书、抽屉、水管、厨房、开车、租房、班级值日。比方里每个角色都要和原文的东西一一对应，并且把对应关系写出来（「快递员 = 那个节点」）。比方在哪一点上失真，当场说破：「这个比方在『成本』上不准，实际是……」。

**比方不许长过「具体到你这件事」。** 比方是引桥，不是目的地——写到读者能接住对应关系就停。故事讲得越圆，越容易让人以为自己懂了。用户反馈「故事是听懂了，可我的项目 / 我的问题到底怎么了还是不知道」，十次有九次是比方写胖了、落地写瘦了。

**〈比方 = 真实〉对照表：** 比方里的角色有 3 个或以上，就单独出一张两列表，一行一个角色——它是比方这一块的收口。散在句子中间的对应关系读者记不住，也没法来回查。两个角色以内，行内写清楚即可，不必单列。右列**必须落到能在屏幕上找到的东西**：节点名、文件路径、参数名，不能只写「那个模块」。格式：

| 比方里的 | 实际是 |
| --- | --- |
| 传送带尽头看照片的人 | 订阅端节点 `perception_node`（`src/percep/node.py`） |
| 传送带上堆着的照片 | `/camera/image_raw` 话题的待处理队列 |

*（ASCII 图）* **默认就画，而且不止一张。** 内容里有几个结构就画几张——流程一张、前后对比一张，别挤成一张四不像。只有当内容里真的既没有流程、也没有层级、对比、顺序、占比时，才跳过。选哪张图、怎么画不歪，见 `references/ascii-patterns.md`。

**具体到你这件事：** 把比方落地。**每一条都要把比方里的角色和真实的东西写在同一句话里**——写「传送带两头的人都得换规矩（= 发消息端和收消息端的 `QoS` 配置），只改一边等于没改」，而不是干巴巴一句「两边都要改」。

**先分清原文在干什么，槽位不一样：**

- **原文在说明一件事 / 一个问题**（讲现状、讲原理、报错、论文段落）——五个槽位：
  1. **这到底是什么** —— 一句话给出本体，不用比方词
  2. **出在哪** —— 原样给出文件路径、函数名、报错原文、命令、行号
  3. **为什么会这样** —— 从原因到现象连成一条线，中间不许跳步
  4. **现在卡在哪一步** —— 已经确认的 / 还没验证的，分开写
  5. **那怎么办** —— **必答，而且三层按顺序写，不许直接跳到第二层：**
     - **先花几分钟验证判断对不对** —— 跑哪条命令、看哪个数，出什么结果才说明上面的诊断成立
     - **确认了就这么修** —— 动哪个文件、哪个参数，改完看到什么现象算修好了
     - **不修会怎样** —— 能拖多久、拖着的代价是什么

     诊断本身还没坐实就直接甩修法，是这一条最常见的翻车方式——所以第一层不许省。
     这五条里原话没有的部分，按开头那条**另起一块标明是我的建议**。

- **原文在让你做一件事**（改法、方案、下一步）——四个槽位：
  1. **动哪个文件、哪个参数** —— 路径和参数名原样写出来
  2. **改完会看到什么现象** —— 可观察的判据，不是「应该就好了」
  3. **下一步做什么** —— 具体到一条命令或一个动作，不是「再观察观察」
  4. **什么情况下会出事**

**这块是必答项，而且它才是正文。** 用户说「比方看懂了，可对不上自己的问题」，就是这块写瘦了——桥搭了一半，人还留在比方那头。

写完就结束。**末尾不附术语表**——术语在正文里已经解释过一次，再列一遍是同一件事做两遍，没人会往回翻。

原文里没有要解释的术语时，只出「一句话 + 具体到你这件事」两块，总长不超过原文的 1.5 倍。术语密集的短句照常走完整结构——每个术语允许多写两三句，但别为了凑满结构硬展开。

## 裁决结构（球被踢回给用户时用）

**先判断走哪套：原文最后是在「告诉」用户，还是在「问」用户。** 问，就走这套。

典型是我自己刚列了几个方案、几种改法、要不要做某件事，然后让用户定。用户敢不敢拍板，不取决于他懂不懂技术，取决于**他能不能看出选错了会怎样**。所以这套的重心不是解释，是**把每条路的代价摆出来**。

**你要拍的板是：** 一句话说清这个决定本身。20–40 字，不带术语。

**〈图，这套里是必画的〉** 两个选项用「选项对比」（模板 9），选项之间有前置条件、要一步步问的用「决策树」（模板 10）。选项本身很难懂时，图前面再加个比方；选项好懂、只是不知道怎么挑，就跳过比方直接上图。

**每条路通向哪：** 一个选项一段——选它之后会发生什么、代价是什么、多花多少时间或钱。**掉头回不来的那条，单独加粗标出来**（数据删了、接口发出去了、格式定死了别人已经在用）。可逆和不可逆混在一起讲，是这块最容易翻车的地方。

**只有你能定的是：** 收在这里。挑明这个决定卡在哪个信息上，而那个信息只有用户手里有——deadline、预算、这块以后谁维护、这批数据要不要留档。**这才是它需要「裁决」而不是我直接做的原因**，说清楚了，用户就知道自己该答什么。

原话里如果已经偏向某个选项，把这个倾向挑明（「刚才那段其实已经在推荐 B，理由是……」）——用户经常看不出来。想给自己的建议可以给，但按开头那条**另起一块标明是我的判断**，别和原话的倾向混在一起。

看懂代价结构之后，常常能拆出一个原话没列的选项（「先按 B 跑一周，确认没事再执行 A」——用一周的代价换掉那个不可逆）。**发现了就写出来**，别硬塞回三选一。这是裁决结构最值钱的产出。

走这套之前先读 `references/decision-example.md`，那是一个完整的选择题重讲示例。

## 语言硬规矩

1. **原词和白话解释必须并排出现，就在读者读懂的那一句里。** 写法是「白话说法（原话叫 X）」或「`X`（白话解释）」，两种都行，但原词不许被抹掉——用户看懂之后还要用这个词跟同事交流。英文缩写尤其不许裸奔：`API`、`RAG`、`QoS`、`SLAM` 第一次出现就给中文说法。**写完「简单来说」又扔出一串没解释的术语，是这个 skill 最常见的翻车方式。**
2. **原文里的专有名词一律原样搬过来，不许换成「那个文件」「那个报错」「某个参数」。** 路径、文件名、函数名、报错原文、数字、命令、分支名、提交号——这些**不需要解释，需要的是照抄**。术语要并排解释，锚点要原样保真，是两回事。读者就是靠这些字去自己屏幕上对号入座的；抹成代词，译文立刻退化成一个跟他无关的故事。
3. 一句话只说一件事，30 字以内。长句拆开。
4. 说口语，不说公文：把「即」「基于」「通过……实现」「进行……处理」「在……场景下」「具备……能力」换成「就是」「用」「做」「在……的时候」。
5. 数字给参照物：「300 毫秒」→「大概眨一次眼」；「1.2 GB」→「一部高清电影的四分之一」；「7B 参数」→「比手机上跑的模型大十几倍」。
6. 准不准比顺不顺口重要。宁可多写一句「但有个前提」，也不把结论说歪。
7. 平视用户：「这很简单」「显而易见」「众所周知」一律不用。

成没成只有一条判据：**用户看完，能用自己的话跟同事复述一遍。**

## 发出前扫一遍

- [ ] 原话里的每个术语，都在正文里跟白话并排出现过吗？还有裸奔的英文缩写吗？
- [ ] 比方从头到尾是同一个吗？每个角色都对上号了吗？
- [ ] 原话的前提、限制、风险，逐条还在吗？
- [ ] 「具体到你这件事」里，每一条都同时出现了比方里的角色和真实的东西吗？
- [ ] **读者能指着自己的屏幕说出「就是这个文件 / 这一行 / 这个报错」吗？** 说不出来，就是锚点没给够，回去把路径、报错原文、参数名补上。
- [ ] **读者读完知道下一步干什么吗？** 只讲清了「你出了什么事」、没讲「那怎么办」，就是只翻了一半。原话里没方案的，另起一块给了建议、并标明是我的判断了吗？
- [ ] **把比方那几段整个删掉，剩下的还能让人动手吗？** 剩下一堆「下游」「策略」「两边配置一致」，就是比方在替正文顶包——砍比方，补锚点。
- [ ] 该画的图都画了吗（一个结构一张）？宽度 ≤ 60 列，等宽字体下不会折行？
- [ ] 走裁决结构时：不可逆的那条标出来了吗？「只有你能定的是」写了吗？

## 收尾

每次结束都留一句：

> 比方对得上你的实际情况吗？哪一块还是糊的，点出来，我只把那一块再拆细。
